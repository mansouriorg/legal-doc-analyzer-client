# Legal Doc Analyzer - client

The page of Legal Doc Analyzer. A person uploads a contract (a PDF or a Word `.docx` file) and reads a summary of it and a list of its clauses, each with a risk (low, medium or high) and a short explanation. By default the server saves each analysis, so it can be opened again later, questioned, or deleted. A box on the start page lets the person leave one analysis unsaved. The reading is done by the server in the `server` folder, which asks an AI service. The AI service can be a free model on your own computer ([Ollama](https://ollama.com)), so the text of a document does not have to leave it.

The result is a first reading by a language model. It can miss a clause or get one wrong, and it is not legal advice.

The page is built with [Next.js](https://nextjs.org) 16 (App Router), React 19 and Tailwind CSS 4.

## What it does

- The start page (`/`, "New Analysis" in the navigation bar) takes a PDF or `.docx` file of up to 10 MB, sends it to the server and shows the analysis. While the server works, the page shows a loading screen with a button "Stop the analysis" (see "Stopping an analysis" below). A box "Do not keep this analysis" under the upload zone asks the server not to save that analysis (see "Keeping or not keeping an analysis" below).
- The History page (`/dashboard`, "Document History") lists the saved analyses, the newest first.
- The saved report page (`/documents/<id>`) shows one saved analysis. From there the person can ask questions about it, or delete it.
- When the server cannot be reached or gives an error, the page says so. It never shows made-up data on its own. The start page can show a clearly labelled demo example, but only when the person clicks for it.

## Quick start

You need Node.js 22.18 or newer (the tests need it), [pnpm](https://pnpm.io), and the server of this project, which needs an AI service. The README in the `server` folder shows how to set up Ollama, which is free and needs no account.

1. Start the server first: in the `server` folder, run `pnpm start:dev`. It listens on port 3001.
2. In the `client` folder, install the packages: `pnpm install`.
3. Start the page: `pnpm dev`.
4. Open http://localhost:3000 in a browser and upload a PDF or a Word file.

The page finds the server at `http://localhost:3001` unless you set another address (see "Changing the server address" below). The server accepts calls from the page only when the page is opened at http://localhost:3000 (the `CLIENT_ORIGIN` setting of the server).

The page uses the Geist fonts through `next/font/google` (`app/layout.tsx`). Next.js downloads them from Google Fonts when it builds the page and serves them itself, so the browser sends no request to Google. That means `pnpm dev` and `pnpm build` can need an internet connection. What happens without one was not tried.

## Changing the server address

The page calls the server at `http://localhost:3001`. To use another address, set `NEXT_PUBLIC_API_URL` when you start the page, for example `NEXT_PUBLIC_API_URL=http://192.168.1.20:3001 pnpm dev`.

- The address starts with `http://` or `https://`. A slash at the end is removed. A path such as `https://example.com/api` is kept, and the calls are added after it. The address may not contain a user name, a password, a space, a line break, `?` or `#`.
- When the setting is not there or is empty, the address stays `http://localhost:3001`. A setting that cannot be used is not replaced by that address. Every call fails with a message that names `NEXT_PUBLIC_API_URL`, so a typo does not go unnoticed. The upload page and the History page show that message. The saved report page shows its usual "Unable to load document" text, and the real message is written to the terminal where `pnpm dev` runs.
- Next.js puts the value into the code of the page when it builds it. With `pnpm dev`, the value is read when `pnpm dev` starts, so stop it and start it again after a change. For a build, give the setting to `pnpm build`, for example `NEXT_PUBLIC_API_URL=http://192.168.1.20:3001 pnpm build`, and build again after a change. A page that was built earlier keeps the value it was built with.
- Give the setting to `pnpm build`, not only to `pnpm start`. When the files that `pnpm build` wrote were looked at (Next.js 16.2.2), a build made without the setting had no reference to `NEXT_PUBLIC_API_URL` left in the code for the browser, but some of the code that runs on the computer of the page still read it when it runs. A page built in that way and started with `NEXT_PUBLIC_API_URL=http://127.0.0.1:1 pnpm start` showed that address on the History page, so a value given only to `pnpm start` does reach the History page. The saved report page asks the server from the same computer, so it most likely does the same. The upload, the Delete buttons and the question box run in the browser and most likely keep the default address, and then the pages use two addresses. Only the History page was tried, once, on one computer, with nothing listening at that address. The rest comes from the build files.
- The value is sent to the browser as part of the page, so it is not a place for a password.
- The History page and the saved report page ask the server from the computer that runs the page. The upload, the Delete buttons and the question box ask it from the browser. The address must work from both. `localhost` always means the computer that makes the call.
- The server accepts calls from the browser only from the address in its `CLIENT_ORIGIN` setting (http://localhost:3000 by default). If you open the page at another address, change `CLIENT_ORIGIN` of the server as well. This client does not change the server.
- A value set in the terminal wins over a file. Next.js also reads the setting from a file `.env.local` in the `client` folder, and `.gitignore` keeps files like that out of git. This project does not create that file.
- `pnpm test` does not depend on the setting, because `services/api.test.mjs` clears it first. `services/apiAddress.test.mjs` and `tests/server-address.test.mjs` test the address and keep this text in line with the code.
- Not tried: a running page with a server at another address, the saved report page when the value is given only to `pnpm start`, and the upload, the Delete buttons and the question box in a browser. The tests use a stand-in for the network.

## Backend endpoints this client expects

The client talks to the NestJS server at http://localhost:3001 by default (see "Changing the server address" above and `services/api.ts`).

- `POST /analyze` - upload a document and get the analysis back. The file is sent as the form field `document`. When the box "Do not keep this analysis" is ticked, the page also sends the form field `save` with the value `false`. When it is not ticked, no `save` field is sent. The call is `analyzeDocument` in `services/api.ts`. The browser only accepts .pdf and .docx files up to 10 MB (see `services/uploadRules.ts`). An old .doc file is refused with a message that tells the person to save it as .docx or as a PDF, because the server cannot read it. The server must check this again, because browser checks can be bypassed. If this call fails, the page shows the error. It offers a clearly labelled demo example only when the user clicks for it, and never shows demo data on its own.
- `GET /documents` - the list of saved analyses for the History page: `{ documents, total, unreadable }`. The newest come first, at most 100 rows. A row has the id, the name, the time of saving and the number of clauses per risk level, but not the clauses (see `listDocuments` in `services/api.ts`). A row that is not usable is left out, and the page never shows invented rows.
- `GET /documents/:id` - one saved analysis, or a 404 when it does not exist.
- `DELETE /documents/:id` - delete one saved analysis for good. The server answers 204 with no body when it deleted it, and a 404 with its own text when no analysis has this id. The Delete button of the saved report page and the Delete button of each row of the History page use it (see `deleteDocument` in `services/api.ts`).
- `POST /documents/:id/ask` - ask a question about a saved document. Body: `{ question, history }`, where `history` is the earlier messages, each as `{ role: "user" | "ai", content }`. Answer: `{ answer }`. The question box of the saved report page uses it (see `askDocumentQuestion` in `services/api.ts` and "Asking questions about a saved analysis" below).

The server answers 200 with the analysis, or with one of these errors:

- 400 (the file was not accepted), 415 (an old .doc file), 422 (a password, a damaged file or no text in it), 502 (the AI service gave an error), 503 (the AI service cannot be used now) and 504 (it was too slow): the page shows the message of the server. The messages of 502, 503 and 504 can name the host of the AI service and the setting to change. That helps whoever runs the server. If the server is ever open to the public, replace those messages on the server with a general text first.
- 413 (more than 10 MB): the page shows its own text, because a proxy in front of the server can also answer 413.
- Any other status, such as 500: the page shows only the status.

A real analysis takes from a few seconds to a minute or more, depending on the model and the document. By default the server saves every analysis it makes and sends the `id` and the time of saving (`savedAt`) with the answer. When it could not save, or when saving is turned off (the setting `SAVE_ANALYSES` of the server, or the box on the start page), the answer has neither, and a note says so. Questions about a saved analysis are a separate call, described under "Asking questions about a saved analysis" below.

## Results page

- On a phone or tablet (below 1024 px wide) the whole page scrolls as normal. The summary and clauses come first and the preview of the original document comes after them.
- On a wide screen the preview is on the left and the analysis is on the right, and each side scrolls by itself.
- The preview works for PDF files only. A browser starts a download when a Word file is put in a frame, so Word files show a short message instead (see `services/previewRules.ts`).
- A saved document has no file, so it shows the analysis alone, in one centred column.
- Under the title, the page shows when the server saved the analysis, for example "Saved 25 Oct 2026, 17:30 UTC+1" (the time is written as described for the History page below). The saved page has a link back to the history.
- The saved page has a red "Delete this analysis" button under the document ID (see "Deleting a saved analysis" below).
- Under the analysis the saved page has a box "Ask about this analysis", and a link under the document ID jumps to it (see "Asking questions about a saved analysis" below).
- At the top of the results there are two buttons, "Print or save as PDF" and "Download as text" (see "Printing and downloading an analysis" below).

## Printing and downloading an analysis

- The results have two buttons at the top, next to the title of the document: "Print or save as PDF" and "Download as text". The saved page has them, and so has the page right after an upload. They are made by `components/document/ReportActions.tsx`. Nothing is sent to the server: both buttons use the analysis that the page already has, so they also work for an analysis that was not kept.
- "Print or save as PDF" opens the print window of the browser. The navigation bar, the buttons, the link back to the history, the Delete button, the question box and the preview of the original document are left out of the printout. The box above the results that deletes a saved copy of the upload page is left out too. The notes, the summary and every clause are printed in one column, and a clause is not split between two pages when it fits on one. The last line is the warning that this is a first reading by an AI model and not legal advice. To get a PDF, choose "Save as PDF" as the printer. While the window is open, the title of the page is the name of the report (for example "NDA-analysis"). Many browsers offer the title of the page as the suggested name of the PDF, but this depends on the browser.
- "Download as text" saves a plain text file, for example `NDA-analysis.txt`. It holds the name of the document, when it was saved (on the clock of the computer, as on the page), the document ID, the notes, the summary, and every clause with its risk, its original text and its implication. It ends with the same warning, and a line at the top says so when the analysis is the built-in demo example.
- The functions that write the text and the file name are in `services/exportReport.ts`. A character that a file system refuses is replaced by `_`, at most 80 characters of the name of the document are used, and a name always ends with `-analysis.txt`.
- The questions and answers of the question box are not in the printout or in the file. The page does not save them either.

## Notes about an analysis

The server can send `notes` with an analysis: things the person should know, such as a warning that the document contains words aimed at an AI, or that only part of a long document was read. The results page shows them in a highlighted box above the title (see `cleanNotes` in `services/api.ts`). It shows only texts, without empty ones and repeats, at most 10 notes of at most 500 characters each. The demo example has no notes.

## Keeping or not keeping an analysis

- The start page has a box "Do not keep this analysis" under the upload zone (`app/page.tsx`). It starts empty. The saved files hold quotes from the document, so a person who does not want them in the saved files of the server can tick the box before clicking "Analyze Document".
- Not ticked (the default): the page sends only the file, and the server does what it is set to do, which is to save the analysis. Ticked: the page also sends the form field `save` with the value `false` (`analyzeDocument(file, { keep: false })` in `services/api.ts`).
- The box keeps its state while the page is open, also after "Analyze Another Document" and after an error, so that the next document is not saved by mistake. Leaving the page and coming back, or reloading it, clears the box. The choice is not stored anywhere.
- An analysis that was not saved is shown like any other, with a note of the server that says why it was not saved. It has no "Saved" time under the title, it is not in the History list, and no question can be asked about it later, because the question box is only on the saved report page. It is gone when the person leaves the page or analyzes another document. The original file on the computer of the person is not touched.
- The server can also be set to save nothing (`SAVE_ANALYSES=false`, see the README of the server). The page cannot know that before an analysis, so the box is still there, and the note of the server says that saving is turned off.
- A server that is older than this choice does not know the field `save` and saves the analysis anyway. The page notices it: the answer has an `id` although the person asked not to keep the analysis. It then puts a note first, "You asked not to keep this analysis, but the server saved it anyway...", shows a box above the results with a button "Delete the saved copy now" (see "Deleting a saved analysis"), and the person can also delete the saved analysis in the History list (see `SAVED_ANYWAY_NOTE`, `savedAgainstChoice` and `withoutSavedCopy` in `services/api.ts`). This is tested with a stand-in for the answer of the server, not with an old server.
- The tests read the text of the source files and stand in for the server (`tests/keep-choice.test.mjs`, `services/api.test.mjs`). The box was not tried in a browser. The server was tested with `save=false` by its own tests (see the README of the server), not together with this page.

## Other screens

- The pages sit in a column under the navigation bar and fill the rest of the window, so a short page does not get a scroll bar of its own.
- The loading screen only describes the work (see `components/ui/LoadingState.tsx`). It shows no progress bar, because the client cannot know how far the server is. It tells the person that a long document can take a minute or more. The button that stops the analysis is under it (see "Stopping an analysis").
- The loading spinners stand still when the system is set to reduce motion.
- The error screen and the not-found screen both link back to the start page.
- The not-found screen (`app/not-found.tsx`) shows "404" and "Page not found", but the HTTP status of that response is 200. The loading screen (`app/loading.tsx`) sits above every page, so Next.js starts streaming the page before the saved report page learns from the server that the id does not exist, and the status is fixed when the stream starts. According to the Next.js documentation it then adds a `noindex` tag, so search engines skip the page. The server itself answers a real 404 (`GET /documents/:id`). This is how streaming works in Next.js (see "Status codes" in its documentation of `loading.js`), and the code does not work around it. To get a real 404, the loading screen would have to move from `app/` into `app/dashboard/`, and the saved report page would then have no loading screen. That change has not been made or tried.

## Stopping an analysis

- While the server works on an upload, the loading screen has a button "Stop the analysis" (`app/page.tsx`) and the hint "If you stop, the server is asked to cancel the analysis. Leaving this page does the same." A model on your own computer can need a minute or more for a long document, so the person can stop without closing the tab.
- A click cancels the request of the browser. `analyzeDocument` takes an optional `signal` in its options (from an `AbortController`), and once the signal is aborted the only error it throws is `ANALYSIS_STOPPED_MESSAGE` ("The analysis was stopped before the server answered."). The page goes back to the upload screen with the file still selected and shows a notice, "The analysis was stopped.", with the texts of `services/analyzeFlow.ts`, and the focus moves to the notice. A stop is not a failure, so there is no red box and no "Show a demo example" button. An answer that comes in later is never shown. Choosing another file, or "Analyze Document" again, clears the notice.
- Leaving the page, for example with a click on "Document History" in the navigation bar, stops the analysis in the same way. Before this change that click did not stop the request, so the server could finish the analysis and save it. The loading screen already asks the person to keep the page open.
- The server side: a server whose README has the section "Stopping an analysis" drops its own call to the AI service when the browser drops the request, and saves nothing for that request. If the AI service had already answered, the analysis is saved as usual, and an older server finishes the analysis and saves it in any case. So a saved copy can exist after a stop. The notice says so to a person who did not tick "Do not keep this analysis", and names the History list, where the copy can be deleted.
- What the AI service does with a closed connection is up to the service. For a question, Ollama 0.40.13 with `qwen2.5:7b` ended its work when the connection was closed (see "Tried with a real AI service"). That was not tried for an analysis, and not with this button.
- The call is tested with a stand-in for `fetch` that ends when its signal is aborted, as the real one does (`services/analyzeStop.test.mjs`), and the page by reading its source (`tests/analyze-stop.test.mjs`). The page was also run in Chromium against a stand-in for the server, without Next.js and without the styles. It was not tried with Next.js, with the styles (so not the layout of the button or of the notice), with a real server or with a real model.

## History page

- The page shows the analyses that the server saved, the newest first. It asks `GET /documents` on every visit (`app/dashboard/page.tsx`), so a new analysis is there at once. It shows no made-up rows.
- When the server cannot be reached or answers with an error, the page says so and shows no rows. When nothing is saved yet, it says so and links to the upload page.
- The three numbers at the top are worked out from the rows (`summarizeHistory` in `services/history.ts`): saved analyses, high-risk clauses and documents with a high-risk clause. The server sends at most 100 rows. When there are more, a note says so, and the two risk numbers count only the rows shown. Another note appears when the server could not read some saved files.
- Times are shown on the clock of your computer, with the difference to UTC, for example "25 Oct 2026, 17:30 UTC+1" (a computer set to UTC shows "25 Oct 2026, 16:30 UTC"). The server saves each time in UTC (`savedAt`, such as 2026-10-25T16:30:00.000Z), and the browser works out the local time (`formatLocalTime` in `services/history.ts`, shown by `components/document/LocalTime.tsx`). The server does not know your time zone, so the page it sends first shows the time in UTC (`formatSavedAt`), and the browser replaces it with the local time as soon as the page is ready. For a moment the UTC time can be seen, and a time that is not in UTC shows the UTC time when you hover over it. Your time zone is not sent to the server and not stored. If a browser reports another time zone than the real one, for example because of a privacy setting, the page follows what the browser reports. The same is true of the "Saved" time under the title of a new or a saved analysis. The tests set several time zones in Node, among them half-hour zones and the days when the clocks change, but they do not open a browser.
- Above the list there is a form to search the analyses (`components/document/HistoryFilterForm.tsx`). It has a box "Search by file name" and a list "Risk" with the choices "All analyses", "With High risk clauses", "With Medium risk clauses", "With Low risk clauses" and "Without clauses". The Search button, or the Enter key in the box, applies them. A search with several words finds the file names that contain all of them, in any order. Capital letters and accents do not matter, so a search for "ete" also finds a file name with an accented e. The search text is cut to 100 characters.
- The form is a plain GET form: Search opens `/dashboard?q=...&risk=...`, so it needs no JavaScript, and the address can be bookmarked or shared. Clear (or "Show all analyses" when nothing matches) goes back to `/dashboard`. The page reads the address with `readHistoryFilter` and picks the rows with `filterHistory` (both in `services/history.ts`). A risk value that is not `high`, `medium`, `low` or `none` is ignored.
- Only the list is filtered. The three numbers and the notes under them still describe all saved analyses. While a search or a risk choice is active, "Showing 2 of 12 analyses in the list." says how many rows are shown, and "No analysis matches" appears when none is. The search covers only the analyses in the list (the newest ones, at most 100), and a line under the form says so when some saved analyses are not in the list. Deleting an analysis opens the History page without the search. The tests do not open a browser.
- Below 1024 px wide each document is a card, because a table does not fit on a phone. From 1024 px up it is a table.
- View Report opens the saved analysis at `/documents/<id>`.
- Each row also has a Delete button (`components/document/HistoryRowActions.tsx`). In the table it is in the Action column, next to View Report. On a phone it is under the risk labels. See "Deleting a saved analysis" below.
- After an analysis is deleted, a green note appears under the title: "The saved analysis was deleted from the server. Your original file was not changed." (or "That analysis was already deleted from the server, so nothing more was removed."). The note comes from the address, `/dashboard?deleted=deleted` or `/dashboard?deleted=already-gone`. The page shows one of these two fixed texts and never shows other text from the address. The note is still there when the page is reloaded. "Dismiss" removes it.

## Deleting a saved analysis

- The saved report page (`/documents/<id>`) has a button "Delete this analysis" (`components/document/DeleteDocumentButton.tsx`). A click only opens a question, "Delete this saved analysis?". Nothing is sent to the server until the person clicks "Yes, delete it". "Cancel" or the Escape key closes the question.
- Deleting is for good. The server removes the file of the analysis and there is no recycle bin. The original document on your computer is not touched.
- While the request runs, both buttons are switched off, so a double click sends only one request. The steps are in `services/deleteFlow.ts`.
- When the server answers 204, the page loads the History page again with a normal page load, so the list is read from the server and the deleted analysis is not in it. When the server says that no analysis has this id (a 404 with its own text), the analysis is already gone, and the page says so and goes to the History page too.
- When the server cannot be reached or answers with an error, the page stays, shows what went wrong, and offers "Try again" and "Cancel". A 404 with another text, for example from an older server that has no delete route, is shown as an error and not as "already deleted".
- The call is made from the browser, so the page must be opened at an address that the server allows (`CLIENT_ORIGIN` of the server, http://localhost:3000 by default). At another address the browser blocks the call, and the page says that it could not reach the server.
- Each row of the History page (`/dashboard`) has a Delete button too (`components/document/HistoryRowActions.tsx`). A click opens the same kind of question inside the row, with the name of the document, and nothing is sent until the person clicks "Yes, delete it". "Cancel" or the Escape key closes it. Each row has its own question, so several can be open at the same time.
- After the server answers (204, or 404 with its own text), the History page is loaded again with a normal page load. The list and the three numbers come from the server, so the deleted row is gone, and the page shows the note described under "History page". The Delete button of the saved report page opens the same address, so the note is shown after that too.
- When the server cannot be reached or answers with an error, the row stays, the question stays open and shows what went wrong, with "Try again" and "Cancel".
- The upload page has a third Delete button, for one case only: the person ticked "Do not keep this analysis" and the server saved the analysis anyway (an older server does that, see "Keeping or not keeping an analysis"). A box above the results says so and has a button "Delete the saved copy now" (`components/document/DeleteSavedCopy.tsx`). It works like the other two: a click only opens a question, nothing is sent until the person clicks "Yes, delete it", and "Cancel" or the Escape key closes it. It uses the same call, `DELETE /documents/:id`, and the same steps (`services/deleteFlow.ts`).
- This button does not leave the page. After the server answers (204, or 404 with its own text), the box says that the saved copy is gone and that the analysis stays on the page until the person leaves it. The page then drops what is no longer true: the "Saved" time, the note that the server saved the analysis, and the ID and Saved lines of the text file (`withoutSavedCopy` in `services/api.ts`). The other notes of the server stay. When the server cannot be reached or answers with an error, the question stays open with "Try again" and "Cancel".
- The box is tested by reading its source (`tests/delete-now.test.mjs`), and the two functions of `services/api.ts` and the texts of `services/deleteFlow.ts` have their own tests (`services/savedCopy.test.mjs`). The box was run in Chromium against a stand-in for the server, without Next.js and without the styles. It was not tried with Next.js, with the styles (so not its layout or its printout) or with an old server.

## Asking questions about a saved analysis

- The saved report page (`/documents/<id>`) has a box "Ask about this analysis" under the analysis (`components/document/DocumentChat.tsx`). The person types a question and presses Send or the Enter key. The question goes to `POST /documents/:id/ask`. The box is only on the saved page. The upload page and the History page do not have it.
- While the conversation is empty, the box shows four suggested questions as buttons (`SUGGESTED_QUESTIONS` in `services/chatFlow.ts`): "What are the biggest risks in this document?", "Explain this document in simple words.", "Which clauses should I read most carefully before signing?" and "What obligations does this document create, and for whom?". A click asks that question at once, in the same way as typing it and pressing Send: it goes to the server with the saved analysis, and the page adds nothing else. The focus moves to the list of messages, where "Working on an answer..." and "Stop waiting" appear. The buttons are shown while no question has been answered and none is running, also next to the red box of a first question that failed (a click then asks the new question, and the failed one is dropped, as when another question is typed). Once a question has been answered, they are gone until the page is reloaded. They are fixed texts, written to fit most contracts, so some may not fit a particular document, and the answers can be wrong like any other. The tests read the source text and do not open a browser, and the buttons were not tried with a real model.
- The server answers only from the saved analysis (the summary, the clauses and the notes), not from the whole contract. Answers can be wrong and are not legal advice. The page says so above the box.
- What is sent: the question (at most 1000 characters) and the latest 6 messages of the conversation, each cut to 4000 characters. The server adds the saved analysis. The conversation and the saved analysis both go to wherever that service runs. With a model on your own computer, for example Ollama as in the README of the server, they stay on your computer.
- Nothing is saved. The questions and the answers live only in the open page, and reloading the page clears them. The server does not save them either.
- A small model can take a minute or more. While it works, the page shows the question, "Working on an answer..." with the seconds waited so far (for example "(12 s)", and "(1 min 5 s)" from a minute on), and a button "Stop waiting". The Send button is off and a second question cannot start. The page has no fixed time limit of its own: the server gives up on the AI service after `AI_TIMEOUT_SECONDS` (120 seconds unless it is set otherwise) and answers 504, and the person can stop earlier.
- "Stop waiting" cancels the request of the browser (`askDocumentQuestion` takes an optional `signal`, from an `AbortController`). The question comes back in the red box with "You stopped waiting for the answer.", "Try again" and "Dismiss", and the focus moves to "Try again". A stopped question is not added to the conversation, and an answer that comes later is never shown. Leaving the page, or opening another document, stops the waiting in the same way.
- Stopping also reaches the server. When the browser drops the request, a server that has `src/client-gone.ts` cancels its own call to the AI service: it closes its connection to the service, so the service can tell that nobody waits for the answer any more. What the AI service does with a closed connection is up to the service: one that stops generating is free for the next question, one that does not goes on until it is done. In a live test (see "Tried with a real AI service" below), Ollama 0.40.13 with `qwen2.5:7b` ended the question when the connection was closed. An older copy of the server keeps working on the question until the AI service answers or gives up (`AI_TIMEOUT_SECONDS`).
- The text of a question and of an answer is shown as plain text, with its line breaks. It is never run as HTML.
- When a question cannot be answered, the page shows a red box with the reason, the question, and two buttons, "Try again" and "Dismiss". A question that failed is never sent as an earlier message. The page never shows made-up answers. The reasons are: the message of the server for 400, 502, 503 and 504; "no longer saved" for a 404 with the text of the server, and "may be an older version" for any other 404; a fixed text for a 500 that says the saved file cannot be read, and only the status for any other 500; "the conversation is too big" for 413; an answer without text; and "could not reach the server".
- The call is made from the browser, so the page must be opened at an address that the server allows (`CLIENT_ORIGIN` of the server, http://localhost:3000 by default).
- The box uses light colours only. A screen reader reads out each new message and each error. The waiting text stands still when the system is set to reduce motion.

## Tried with a real AI service

The README of the server ("Tested with a real model") describes a live test of the server with Ollama 0.40.13 and `qwen2.5:7b`: analyzing a document, saving, asking questions, reading, listing and deleting, and the stop of a question. That test called the server directly and did not use this page. The tests in this folder read the text of the source files and do not open a browser. The whole chain (browser, server, Ollama) was not run together for the stop. The stop of an analysis was not tried with a real model at all (see "Stopping an analysis").

## Tests

Run `pnpm test`. The tests use the built-in Node test runner (Node 22.18 or newer) and need no extra packages. They include a few plain text checks (`tests/design.test.mjs`) that keep the design fixes in the styles and the navigation from being undone by accident. `tests/readme.test.mjs` keeps this README true to the code: the commands, the pages and the address of the server that it names must still exist. `tests/keep-choice.test.mjs` keeps the box on the start page, the call that sends the choice and the part of this README that describes them in line with each other. `tests/suggested-questions.test.mjs` keeps the suggested questions, their buttons in the question box and their description in this README in line with each other. `services/exportReport.test.mjs` tests the text of a downloaded analysis and its file name. `tests/report-actions.test.mjs` keeps the two buttons, the print styles and the description in this README in line with each other. The tests do not open a browser. `package.json` has `"type": "module"`, so Node reads the `.ts` files that the tests import as ES modules and prints no warning about them. A file that needs the old `require` style must be named `.cjs`. `tests/module-type.test.mjs` keeps that setting in place and checks that the project has no code of that old style. `services/apiAddress.test.mjs` tests the rules for the address and that every call uses it. `tests/server-address.test.mjs` keeps the code and the text about the address in line with each other. `services/savedCopy.test.mjs` tests how the page finds a copy that the server saved against the choice of the person, and what the page shows once the copy is deleted. `tests/delete-now.test.mjs` keeps the box that deletes that copy, its place on the upload page and the description in this README in line with each other. `services/analyzeStop.test.mjs` tests how the call to the server ends when the analysis is stopped, and the words of the notice that follows a stop. `tests/analyze-stop.test.mjs` keeps the button that stops the analysis, the notice, the request that can be stopped and the description in this README in line with each other.
